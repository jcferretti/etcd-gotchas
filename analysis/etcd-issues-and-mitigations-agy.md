## Scope & Executive Summary

This document is a standalone decision and deployment guide for prospective production adopters of `etcd` (`v3.7.3`) and its Java client `jetcd` (`0.8.7`). It distills the findings of five in-depth source analyses into a concise catalog of open bugs, architectural hazards, failure scenarios, and concrete deployment mitigations across **Leases**, **Watchers**, and **Write Performance**, followed by the key questions an engineering team must answer before putting etcd into production.

### Summary of Claims

1. **Core KV Consistency vs. Peripheral Subsystem Fragility (**High confidence**):**
   etcd's replicated key-value state machine (`Put`, `DeleteRange`, `Txn`, and committed `LeaseGrant`/`LeaseRevoke`) is strictly linearizable, and its Multi-Version Concurrency Control (`MVCC`) revision log preserves event history across leader failovers. However, the subsystems built around that core—**lease renewals/timers**, **watch stream control/bookmarks**, **client libraries (`client/v3`, `jetcd`)**, and **auxiliary packages (`grpcproxy`, `client/v3/leasing`, `etcd/cache`)**—bypass Raft consensus or rely on broken client state machines, creating silent staleness, premature or infinite lease retention, and event-loss hazards.
2. **Leases Break Both Expiration Bounds Across Failovers and Contain Severe Client Leader-Loss Bugs (**High confidence** on code paths and `#22649`/`#22081`/`#22094`; **Moderate confidence** on residual server race schedules):**
   Across leader elections, `lessor.Promote()` resets uncheckpointed lease TTLs to `ElectionTimeout + GrantedTTL`, delaying lock recovery and preventing passive TTL leases from expiring under frequent elections (`k8s#65497`). The Alpha `LeaseCheckpoint` feature (`Default: false`) ignores leases with `TTL <= 300s` and has an open bug ([#22649](https://github.com/etcd-io/etcd/issues/22649)) that silently discards Raft errors when clearing checkpoints on renewal, leaving a shorter server timer than promised to the client. Meanwhile, `WithRequireLeader` in Go `client/v3` ([#22094](https://github.com/etcd-io/etcd/issues/22094), [#22081](https://github.com/etcd-io/etcd/issues/22081)) and stream errors in Java `jetcd` (`LeaseImpl.java:273`) close or fail the user's notification channel on leader loss while **continuing to renew the "lost" lease in the background forever**.
3. **Watchers Claim "Eventual Consistency" While Admitting Events "Might Never Arrive" in a Quorum-Healthy Cluster—Forcing Clients to Poll—and `jetcd` Silently Drops Historical Events on Reconnect (**High confidence**):**
   Etcd explicitly claims to provide *"eventual consistency for Watch"* (`tests/robustness/README.md:111 @ v3.7.3`), which its own specification defines as the liveness property that components *"converge to the same view eventually"* (`tests/robustness/README.md:102 @ v3.7.3`). Yet `etcd-io/website` `content/en/docs/v3.7/learning/api_guarantees.md:36-38` states that *"events in unhealthy clusters might never arrive"*, and `content/en/docs/v3.7/learning/design-client.md:80, 106, 136` admits that even when a cluster **maintains a healthy majority quorum**, a watch stream can *"get stuck with one failed or partitioned node"* forever (`k8s#59848`). Equating eventual consistency (liveness) with prefix safety (*Ordered, Unique, Reliable*, which a permanently silent stream satisfies vacuously) is a fundamental conceptual contradiction. Worse, `WithRequireLeader` fails across nine verified paths—destroying the client's watch channel instead of failing over (`k8s#111116`), dropping partition-window events on `startRev == 0` watches, and being ignored by `grpcproxy`—while `jetcd 0.8.7` overwrites its resumption cursor with the server's tip revision upon receiving `Created` (`WatchImpl.java:267`), **silently dropping all historical events `[startRev, serverRev - 1]` if the stream disconnects during catch-up**. Because a client cannot establish a watcher with guaranteed liveness, clients are forced to bolt on periodic polling or scheduled watch restarts.
4. **Decoupling Leases from Watches Breaks Client-Side Caching and Lock Waiting (**High confidence**):**
   Because gRPC `round_robin` places a client's `LeaseKeepAlive` and `Watch` streams on different cluster members with no causal acknowledgement (`Ack-or-Expired`), a client's lease can stay alive on the leader while its watch stream stalls on a follower. In etcd's Chubby-style cache (`client/v3/leasing`), this split stalls competing writers indefinitely, optimistic client deadlines serve stale cached reads (`#19091`), and a `wc == nil` logic bug causes **every non-owner write to be applied twice** (`2` Raft proposals uncontested, `5` proposals contested).
5. **Write Performance Is Bottlenecked by Both a Synchronous Raft/WAL Pipeline and `bbolt` Copy-on-Write / Synchronous-Delete Stalls (**High confidence**):**
   Every write pays a mandatory Raft WAL `fdatasync` on a non-pipelined `raftNode` loop (`raft.go:185-336`), a 3–4 `fsync` stall on every 64 MB WAL segment rotation (`w.cut()`), an `ext4`/`XFS` unwritten-extent journal commit penalty on every `fdatasync` into `fallocate`d blocks, and a 3-`fdatasync` checkpoint stall every 10,000 entries (`server.go:1215`). In the `bbolt` backend, PR [#17119](https://github.com/etcd-io/etcd/pull/17119) (`batch_tx.go:335`) forces an immediate synchronous `bbolt.Tx.Commit()` (`2x fdatasync`) on **every single `LeaseRevoke`** and **every MVCC compaction batch** because `txBuffer` cannot represent delete tombstones, while aged multi-GiB databases suffer 100ms commit lock stalls, $10\times\text{–}50\times$ CoW compaction write amplification, and stop-the-world `Defrag()` pauses.

## 1. Lease, Lock, and Client-Session Issues & Mitigations

### 1.1 Why Lease Issues Happen (Architectural Root Cause — **High confidence**)
To avoid a Raft quorum write on every heartbeat, etcd replicates `LeaseGrant` and `LeaseRevoke` through Raft into `bbolt`, but keeps lease expiration timers and `LeaseKeepAlive` renewals **only in the Raft leader's volatile memory** (`server/lease/lessor.go:396-456 @ v3.7.3`). Followers set all lease expiries to `forever` (`time.Time{}`). Unlike Google's Chubby, etcd (**High confidence**):
1. Measures leader step-down (`CheckQuorum`) in Raft ticks on `raftNode.start()` (`server/etcdserver/raft.go:183 @ v3.7.3`), which freezes during WAL `fdatasync` disk stalls while `lessor.runLoop()` continues expiring leases on wall-clock time in another goroutine.
2. Emits expiry-driven `LeaseRevokeRequest` proposals with **no Raft term or epoch** (`api/etcdserverpb/rpc.proto:889-894 @ v3.7.3`), while `go.etcd.io/raft/v3` automatically forwards proposals from followers to the current leader (`raft.go:1718-1729 @ v3.7.0`).
3. Overloads a single Lease API for both short-lived active coordination sessions (which need failover extensions) and passive 1-hour TTL garbage collection (which breaks when failover extensions reset TTLs).

### 1.3 Deployment & Application Mitigations for Leases (**High confidence**)

1. **Always fence state mutations and external actions with MVCC revisions (`CreateRevision` / `ModRevision` — **High confidence**):**
   Never rely on `Session.Done()` or local lease timers alone for mutual exclusion. Guard every etcd write with a transactional compare (`If(Mutex.IsOwner())` i.e. `CreateRevision(lockKey) == myRev`, or `Election.Proclaim()`), and pass `myRev` as a monotonically increasing fencing token (Chubby sequencer) to external storage or services.
2. **Do NOT enable `--feature-gates=LeaseCheckpoint=true` on `v3.7.3` (**High confidence**):**
   Leave `LeaseCheckpoint` disabled until open bug [#22649](https://github.com/etcd-io/etcd/issues/22649) (`server/etcdserver/server.go:401-402`) is patched (PR [#22650](https://github.com/etcd-io/etcd/pull/22650)).
3. **Do NOT pass `WithRequireLeader(ctx)` to `clientv3.Lease.KeepAlive(ctx, id)` on `v3.7.3` (**High confidence**):**
   Use default contexts on `KeepAlive` (as `concurrency.NewSession` does) or patch `closeRequireLeader()` (`client/v3/lease.go:376-411`, PRs [#22087](https://github.com/etcd-io/etcd/pull/22087), [#22253](https://github.com/etcd-io/etcd/pull/22253), [#22291](https://github.com/etcd-io/etcd/pull/22291)) to prevent zombie renewals ([#22094](https://github.com/etcd-io/etcd/issues/22094)) and channel corruption ([#22081](https://github.com/etcd-io/etcd/issues/22081)).
4. **In Java `jetcd 0.8.7`, explicitly close the `CloseableClient` inside `StreamObserver.onError()` (**High confidence**):**
   Any application using `leaseClient.keepAlive(leaseId, observer)` must call `closeableClient.close()` inside `observer.onError(t)` so `jetcd` removes the lease from `keepAlives` instead of renewing it forever in the background.
5. **For critical leader election / heartbeats or strict TTL expiration, prefer explicit MVCC keys with CAS over native etcd leases (**High confidence**):**
   Follow Kubernetes's pattern (`coordination.k8s.io/v1` `Lease` in `pkg/registry/coordination/lease/storage/storage.go:36-50`): store a plain MVCC key with an explicit timestamp field updated via compare-and-swap (`ModRevision`). This avoids `Promote()` TTL resets and leader-memory split-brain at the cost of one Raft write per renewal. If native leases are used to batch-expire objects, cap attachments at $\le 500\text{–}1,000$ keys per lease.
6. **Do NOT use `client/v3/leasing` or `etcd grpc-proxy --experimental-leasing-prefix` in production (**High confidence**):**
   The package is unmaintained and contains severe correctness and write-amplification bugs.

## 2. Watcher, Cache, and Proxy Issues & Mitigations

### 2.1 Why Watcher Issues Happen (Architectural Root Cause & The "Eventual Consistency" Contradiction — **High confidence**)
Every watched key-value mutation goes through Raft into each member's local MVCC `bbolt` history (`server/storage/mvcc/watchable_store_txn.go:22-47 @ v3.7.3`), so committed events are never lost on disk when a leader fails over. However, **watch stream operations (`WatchCreateRequest`, `WatchProgressRequest`, `ProgressNotify`, and stream liveness) completely bypass Raft and linearizable `ReadIndex`** (`server/etcdserver/api/v3rpc/watch.go:340-400, 558-570 @ v3.7.3`, **High confidence**).

This architectural split produces a profound conceptual contradiction in etcd's specification (**High confidence**):
- On one hand, etcd claims to implement **eventual consistency** for Watch: *"Etcd provides strict serializability for KV operations and eventual consistency for Watch"* (`tests/robustness/README.md:111 @ v3.7.3`), defining eventual consistency on line `102` as: *"Components may temporarily see different data after an update **but converge to the same view eventually**."*
- On the other hand, etcd's API guarantee documentation states: *"However, there is no limit and events in unhealthy clusters might never arrive"* (`etcd-io/website` `content/en/docs/v3.7/learning/api_guarantees.md:36-38`), and its client design specification admits that even when **the cluster as a whole maintains a healthy majority quorum and is actively committing writes**, *"it is possible that balancer gets stuck with one failed or partitioned node"* and *"Streaming request may get stuck with a partitioned node"* (`content/en/docs/v3.7/learning/design-client.md:80, 106, 136`; see also `client/v3/watch.go:82-83 @ v3.7.3`).

In distributed systems theory, **eventual consistency** is a **liveness (convergence)** guarantee: if a cluster has quorum, all non-faulty subscribers must eventually receive committed updates. Etcd's Watch properties (*Ordered, Unique, Atomic, Reliable*) only define **prefix safety** (if events arrive, they arrive in revision order without gaps—a property that an empty, permanently silent stream satisfies vacuously). Equating *"converge to the same view eventually"* with *"might never arrive"* when a single member of a quorum-healthy cluster is partitioned or apply-stalled is a contradiction in terms. Worse, because a client cannot establish a watcher with guaranteed liveness—and cannot detect from the watch stream alone that its serving member has silently stopped delivering events—the push-subscription utility of Watch is negated unless the client bolts on **periodic polling** (linearizable `KV.Get` `ReadIndex` checks or scheduled watch restarts) (**High confidence**).

### 2.3 Deployment & Application Mitigations for Watchers (**High confidence**)

1. **Never open watches at `startRev == 0`; always use List-then-Watch with `WithRev(listRev + 1)` (**High confidence**):**
   Perform an initial `Get` / list, record `resp.Header.Revision`, and open the watch at `WithRev(resp.Header.Revision + 1)`. Maintain `lastProcessedRev` in your application.
2. **Enable HTTP/2 keepalive pings (`DialKeepAliveTime` / `DialKeepAliveTimeout`) and `WithRequireLeader(ctx)`—and handle channel closure by re-watching from `lastProcessedRev + 1` (**High confidence**):**
   - In Go `clientv3`, `DialKeepAliveTime` defaults to `0` (disabled); explicitly set `DialKeepAliveTime = 30s` and `DialKeepAliveTimeout = 10s` (as Kubernetes does in `factory/etcd3.go:63-64`).
   - Wrap **both** `Watch` and `RequestProgress` contexts in `clientv3.WithRequireLeader(ctx)`. Because `clientv3` and `jetcd` close the watch on `ErrNoLeader` (and `clientv3` may drop the error after `250ms`), treat *any* watch channel closure as a retryable signal to re-open the watch at `WithRev(lastProcessedRev + 1)` (relocating to a full re-list only on `ErrCompacted`).
3. **Poll for liveness and never trust `RequestProgress` alone for linearizable cache reads (apply Kubernetes `KEP-2340` or periodic watch verification — **High confidence**):**
   Because Watch provides only prefix safety—not eventual-convergence liveness—when a serving member is minority-partitioned or apply-stalled, and because `RequestProgress` returns a replica's unfenced local revision (and can be starved server-wide by `#20242`), clients must bolt on polling:
   - Any cache serving linearizable reads must first issue a cheap linearizable `KV.Get(ctx, "/", WithCountOnly(), WithLimit(1))` to obtain the quorum `ReadIndex` revision $R_{\text{lin}}$, wait for the watch cache to reach $R_{\text{lin}}$, and fall back to a direct etcd read on timeout (`KEP-2340`).
   - Background watch consumers that do not serve on-demand linearizable reads must periodically poll the cluster's linearizable revision (via `KV.Get` with `ReadIndex`) or restart/rotate watches when the local watch bookmark lags behind $R_{\text{lin}}$ for longer than a staleness threshold.
4. **Do NOT rely on `jetcd 0.8.7`'s internal watch resumption for historical watches (**High confidence**):**
   In Java, either patch `WatchImpl.processCreated` (`WatchImpl.java:267`, changing `Math.max` so `this.revision` is only set from `Header.Revision` when `this.revision == 0`, and adding `+ 1` on `ProgressNotify` at lines `293, 312`) or manage reconnection in application code using your own `lastProcessedModRevision + 1`.
5. **Drain `WatchChan` promptly and avoid burst cancellations ($>16$) on a shared context (**High confidence**):**
   To avoid unbounded `ws.buf` growth, the `250ms` close-error drop, and the `#18879` 4-way cancellation deadlock, drain `WatchChan` into a bounded application queue and rate-limit concurrent watch cancellations.
6. **Always pass `--bump-revision <delta> --mark-compacted` during `etcdutl snapshot restore` (**High confidence**):**
   Ensure any restored cluster starts at a revision strictly higher than any revision previously observed by clients, forcing watchers to receive `ErrCompacted` and re-list cleanly ([#14303](https://github.com/etcd-io/etcd/issues/14303)).
7. **Do NOT deploy `grpcproxy` for watch multiplexing or use `etcd/cache` in `v3.7.3` (**High confidence**):**
   Both contain unfixed liveness/event-loss bugs ([#21813](https://github.com/etcd-io/etcd/issues/21813), [#19710](https://github.com/etcd-io/etcd/issues/19710), [#22614](https://github.com/etcd-io/etcd/issues/22614)).

## 3. Write Performance & Persistence Pipeline Issues & Mitigations

### 3.1 Why Write Performance Issues Happen (Architectural Root Cause — **High confidence**)
Every write in etcd `v3.7.3` traverses two distinct persistence layers (**High confidence**):
1. **The Consensus & WAL Layer (`server/etcdserver/raft.go`, `server/storage/wal/`):** A single-threaded `raftNode` loop that synchronously writes and `fdatasync`s every batch to a 64 MB segmented Raft WAL before advancing Raft state.
2. **The State-Machine Backend (`server/storage/backend/`, `bbolt`):** An `mmap`-backed, single-writer Copy-on-Write (CoW) B+tree. While normal `Put` and `DeleteRange` operations append sequential 17/18-byte revision keys (`UnsafeSeqPut`) into an in-memory buffer (`batchTxBuffered`) committed every `100ms` or `10,000` ops, **backend deletions (`UnsafeDelete`), periodic commits, MVCC compactions, and 10,000-entry checkpoints** trigger severe lock stalls and synchronous `fdatasync` amplification.

### 3.3 Deployment Mitigations, Diagnostics, and Architectural Options

#### Step 1: Zero-Code Operational Mitigations (Apply Immediately in Production — **High confidence**)
1. **Isolate `--wal-dir` on dedicated local NVMe storage and a separate filesystem from `--data-dir` (**High confidence**):**
   - Never run etcd on network-attached storage with high tail `fdatasync` latency without sizing timeouts accordingly, or on shared disks.
   - Put `--wal-dir` (`member/wal`) and `--data-dir` (`member/snap/db`) on **separate filesystems/mounts** (prefer `XFS` or separate NVMe namespaces). On `ext4` (`data=ordered`), sharing a filesystem causes `fdatasync` on the Raft WAL to flush dirty OS page-cache blocks from the backend store into the `jbd2` journal ([cockroach#16624](https://github.com/cockroachdb/cockroach/issues/16624)).
2. **Keep `bbolt` database size well below RAM (`2–8 GiB`) and run `Defrag()` only as a rolling follower operation (**High confidence**):**
   - Configure `--auto-compaction-mode=periodic` or `revision` to bound history, and monitor `etcd_mvcc_db_total_size_in_bytes` vs. `etcd_debugging_mvcc_db_total_size_in_use_in_bytes`.
   - Never run `etcdctl defrag` on the active leader or across all nodes simultaneously: defragment followers one at a time, then call `MoveLeader` before defragmenting the former leader.
3. **Tune batch and checkpoint flags for write-heavy workloads (**High confidence**):**
   - Increase `--snapshot-count` (default `10,000`, e.g., to `50,000–100,000`) if the every-10,000-entry `s.snapshot()` triple-`fdatasync` spike is visible in p99 latency (trading slightly longer WAL replay on crash recovery).
   - Tune `--backend-batch-interval` (default `100ms`) and `--backend-batch-limit` (default `10,000`) to balance commit frequency against dirty-page accumulation.
4. **Minimize native `LeaseRevoke` churn on write-heavy clusters (**High confidence**):**
   Because every `LeaseRevoke` triggers a synchronous `bbolt` `fdatasync` (`batch_tx.go:335`), avoid creating and revoking hundreds of short-lived leases per second.

#### Step 2: 1-Day Bottleneck Diagnosis on Target Hardware (Before Changing Code — **High confidence**)
Before considering code patches or storage engine changes, run two checks on your target hardware ([`storage-agy.md` §6](storage-agy.md), [`wal-replacement-agy.md` §6](wal-replacement-agy.md)):
1. **Prometheus Histogram Attribution (**High confidence**):**
   - Compare `etcd_disk_wal_fsync_duration_seconds` against `etcd_disk_backend_commit_duration_seconds`.
   - If `rate(etcd_disk_backend_commit_duration_seconds_count[1m]) >> 10/s`, you are hitting the **`pendingDeleteOperations > 0` synchronous commit trap** (`batch_tx.go:335`) from `LeaseRevoke` or compaction.
   - If `rate(etcd_disk_backend_commit_duration_seconds_sum[1m]) > 0.20` (backend commit lock held $>20\%$ of wall time), `bbolt` is a primary bottleneck; if `< 0.05` and WAL fsync dominates, replacing `bbolt` alone will not help.
2. **The $2 \times 2$ `tmpfs` Ceiling Matrix (`tools/benchmark` on an aged 6 GiB DB — **High confidence**):**
   Run `tools/benchmark` across four mount combinations: (1) WAL on disk, Snap (`bbolt`) on disk; (2) WAL on disk, Snap on `tmpfs` (**exact ceiling of replacing `bbolt` alone**); (3) WAL on `tmpfs`, Snap on disk (**exact ceiling of optimizing the WAL alone**); and (4) both on `tmpfs` (**combined ceiling**).

#### Step 3: Surgical Patches vs. Full Persistence Redesign (If Maintaining a Fork)
If Step 2 proves that etcd's storage layer cannot meet your throughput or p99 latency targets with operational tuning alone:
- **Option 1 — Surgical 80-Line `txBuffer` Tombstone Patch ([`storage-agy.md` §5.2](storage-agy.md) — **High confidence**):**
  Add a `deleted bool` tombstone marker to `txBuffer` (`server/storage/backend/tx_buffer.go`) and remove `|| t.pendingDeleteOperations > 0` from `batchTxBuffered.Unlock()` (`batch_tx.go:335`), plus remove redundant `ForceCommit()` in `kvstore_compaction.go:90`. This restores 100ms batching across `LeaseRevoke` and compaction with `< 100 LoC`.
- **Option 2 — Co-Designed `pebble` Backend + `RaftLogEngine` Fork ([`storage-agy.md` §3–§5](storage-agy.md), [`wal-replacement-agy.md` §3–§6](wal-replacement-agy.md) — **High confidence** on architectural design; **Moderate confidence** on ~4,150 LoC estimate and target-hardware speedup ratios):**
  - *Why `pebble` (`v2.1.7`), not `grocksdb` (**High confidence**):* `mvcc.rangeKeys` issues $N$ backend point lookups per `Range` query; `grocksdb` pays $20,000\text{–}60,000$ `cgo` boundary crossings per 10k-key range scan and breaks static Go builds, whereas pure-Go `pebble` provides `pebble.IndexedBatch` (natively indexing delete tombstones) and zero `cgo` overhead.
  - *Why NOT a single unified LSM for both Raft log and MVCC (**High confidence**):* Storing short-lived Raft entries inside the same LSM as MVCC state doubles compaction I/O and allows LSM L0 compaction stalls to block `r.storage.Save()`, causing Raft heartbeat timeouts and leader elections.
  - *Target Fork Architecture (~4,150 LoC across 4 modular phases — **Moderate confidence** on LoC estimate):* (1) Enable `AsyncStorageWrites` (`raft.go`) with explicit guards for open bugs `raft#551` and `raft#543`; (2) replace `wal.WAL` with `RaftLogEngine` built on `pebble/record.LogWriter` (`WriteWALSyncOffsets`, group commit, and pre-written recycled 64 MiB `.log` files that eliminate both `w.cut()`'s 4-fsync stall and `ext4`/`XFS` unwritten-extent journal commits while fixing `isTornEntry`); (3) run `pebble` in `pebble.NoSync` mode (**0 `fdatasync`s** on the apply or 100ms commit path) with a background `db.LogData(nil, pebble.Sync)` checkpoint barrier; and (4) sort `revpairs` in ascending `Revision` order in `mvcc.rangeKeys` using a single forward-seeking `pebble.Iterator` (`TrySeekUsingNext`) so range reads match or beat `bbolt`.

## 4. Decision Guide for Prospective Adopters: Questions to Ask & What to Understand

If you are evaluating etcd for a new or existing production system, use the questions and principles below to determine your risk exposure before committing to deployment.

### 4.1 Seven Questions to Ask About Your Workload and Architecture (**High confidence**)

1. **How will your application use etcd Leases—for active coordination (locks/elections) or passive TTL garbage collection? (**High confidence**)**
   - *Why it matters:* If you use native leases for passive TTL cleanup (like Kubernetes `Event`s), leader failovers will reset their full TTLs (`lessor.Promote`), and enabling `LeaseCheckpoint` exposes you to bug [#22649](https://github.com/etcd-io/etcd/issues/22649). If you revoke leases at high rates ($>50/\text{s}$) or attach $>1,000$ keys to a single lease, every revocation forces a synchronous `bbolt` `fdatasync` (`batch_tx.go:335`) and risks apply-loop stalls (`k8s#96836`).
   - *Next step:* Ask whether passive expiration can be moved to a background sweeper over indexed timestamps, and whether coordination heartbeats should use CAS-updated MVCC keys (`ModRevision`) instead of `LeaseKeepAlive`.
2. **Do any of your services or external side effects rely on `Session.Done()` or `Mutex.Lock()` without transactional revision fencing? (**High confidence**)**
   - *Why it matters:* Client lease deadlines are optimistic (`receipt_time + TTL`), server failovers can prematurely revoke leases (`R1`–`R2`) or leak zombie renewals (`#22094`, `jetcd` `onError`), and `Mutex.Unlock()` is unfenced (`#22082`).
   - *Next step:* Audit every critical section to verify that all etcd writes include `If(CreateRevision(lockKey) == myRev)` and all external calls pass `myRev` as a verified fencing token.
3. **Which client library will your services use—Go `client/v3` or Java `jetcd`? (**High confidence**)**
   - *Why it matters:* Java `jetcd 0.8.7` is pre-1.0, tests against outdated `etcd v3.5.14`, silently drops historical watch events `[startRev, serverRev - 1]` if a stream disconnects after `Created` (`WatchImpl.java:267`), has an off-by-one bug on `ProgressNotify`, and leaks infinite background lease renewals after `onError`. Go `client/v3` disables HTTP/2 keepalives by default (`DialKeepAliveTime == 0`) and has open `WithRequireLeader` bugs (`#22081`, `#22094`, and the 9 watch teardown/failover failures).
   - *Next step:* If using Java, budget engineering work to wrap or patch `WatchImpl.java` and `LeaseImpl.java` before production use.
4. **Do your applications maintain in-memory caches via Watch—and what happens if a watch stream goes permanently silent while the cluster still has quorum? (**High confidence**)**
   - *Why it matters:* Despite claiming *"eventual consistency for Watch"* (`tests/robustness/README.md:111`), etcd Watch guarantees only prefix safety (event sequence continuity within retained history), **not** eventual convergence (liveness) or freshness. Even when the cluster maintains a healthy majority quorum, a watch on a single partitioned or apply-stalled member can silently stop delivering updates forever (`api_guarantees.md:38`, `design-client.md:136`, `k8s#59848`), and `RequestProgress` can be starved server-wide by a single catching-up watcher (`#20242`).
   - *Next step:* Because etcd provides no way to set up a watcher with guaranteed liveness, budget client engineering to add periodic liveness polling (comparing the watch revision against a linearizable `KV.Get` `ReadIndex` per `KEP-2340` or rotating stalled watches) and verify your reconnect loop handles `ErrNoLeader` and `ErrCompacted`.
5. **What is your expected database size, write rate, compaction retention, and multi-key `Range` scan size? (**High confidence**)**
   - *Why it matters:* Below ~1 GiB with low lease churn on fast NVMe, `bbolt` performs well and write latency is bounded by Raft WAL `fdatasync`. Above 2–8 GiB with heavy churn and compaction, `bbolt` suffers 100ms commit lock stalls, CoW write amplification, and stop-the-world `Defrag()` pauses.
   - *Next step:* Run the 1-day $2 \times 2$ `tmpfs` benchmark matrix (§3.3 Step 2) on your target hardware at your projected aged dataset size before finalizing capacity plans.
6. **What is your storage hardware and filesystem topology? (**High confidence**)**
   - *Why it matters:* WAL `fdatasync` latency directly governs both write throughput and Raft leader stability (since a slow `fdatasync` freezes `raftNode` tick processing while lease timers keep running).
   - *Next step:* Confirm that each etcd member has dedicated local NVMe storage with `--wal-dir` and `--data-dir` on separate filesystems/mounts.
7. **What is your disaster-recovery and maintenance runbook for compaction, `Defrag()`, and `etcdutl snapshot restore`? (**High confidence**)**
   - *Why it matters:* Restoring a snapshot without `--bump-revision <delta> --mark-compacted` silently breaks active watchers (`#14303`), and running `Defrag()` on a live leader freezes the cluster.
   - *Next step:* Codify `--bump-revision --mark-compacted` into all backup/restore automation and enforce follower-only rolling `Defrag()`.

### 4.2 Five Core Realities Teams Must Understand Before Deploying etcd (**High confidence**)

1. **etcd is a linearizable log of revisions, not a Chubby-style session service (**High confidence**):**
   In Chubby, locks, caches, and notifications are bound to one master-held session `KeepAlive` (`Ack-or-Expired`). In etcd, `KV`, `Lease`, and `Watch` are independent primitives that gRPC `round_robin` routes to different cluster members. Your application code—not etcd—is responsible for bridging them safely using `Revision` numbers.
2. **Watch does NOT provide eventual consistency (liveness) on its own—and `WithRequireLeader` is a blunt partition detector, not transparent failover (**High confidence**):**
   Equating *"eventual consistency"* (`tests/robustness/README.md:102, 111`) with *"events in unhealthy clusters might never arrive"* (`api_guarantees.md:38`) when a single node in a quorum-healthy cluster is impaired (`design-client.md:80, 106, 136`) is a conceptual contradiction: Watch provides **prefix safety**, not **liveness**. Enabling `WithRequireLeader` cancels streams on minority-partitioned nodes (`ErrNoLeader`), but it is blind to apply-loop stalls, destroys your client watch stream instead of failing over, and causes reconnections during routine 1-second elections to fail immediately. To achieve true eventual consistency, your watch consumer loop must re-open closed watches at `lastProcessedRev + 1` **and** pair Watch with periodic linearizable `ReadIndex` polling (`KV.Get`) or scheduled watch rotation.
3. **Disk I/O stalls are correctness events for Leases, not just performance regressions (**High confidence** on code coupling; **Moderate confidence** on `R1`/`R2` race schedules):**
   Because leadership step-down (`CheckQuorum`) is clocked by the same `raftNode` goroutine that blocks on `WAL.Save()` (`fdatasync`), a multi-second disk stall freezes the leader's step-down clock while wall-clock lease timers continue to run, exposing the cluster to the residual post-stall windows (`R1`–`R3`).
4. **Upstream test suites (`tests/robustness` and Antithesis) do not test `KeepAlive` or lease expiration (**High confidence**):**
   As verified in `tests/robustness/traffic/traffic.go:50 @ v3.7.3`, etcd's linearizability robustness suite grants 2-hour leases (`7200s`) so they never expire, never calls `KeepAlive`, and disabled `ProgressNotify` validation (`PR #20240`) after `#20242`. Do not assume lease failover or watch progress edge cases are covered by upstream CI.
5. **Avoid etcd's secondary proxy and caching packages (`grpcproxy`, `client/v3/leasing`, `etcd/cache`) (**High confidence**):**
   Production reliability in etcd is concentrated in the core `KV` store and carefully written direct `client/v3` consumers (following `kube-apiserver`'s defensive patterns). The auxiliary caching and proxy packages contain critical unfixed bugs in `v3.7.3`.
