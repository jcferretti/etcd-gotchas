## Scope & Executive Summary

This document is a standalone decision and deployment guide for prospective production adopters of `etcd` (`v3.7.3`) and its Java client `jetcd` (`0.8.7` / `0.8.8`). It distills the findings of five in-depth source analyses—together with the Jepsen analyses of [`etcd 3.4.3`](https://jepsen.io/analyses/etcd-3.4.3) and [`jetcd 0.8.2`](https://jepsen.io/analyses/jetcd-0.8.2) and upstream issue-triage history—into a concise catalog of open bugs, architectural hazards, failure scenarios, ecosystem/governance risks, and concrete deployment mitigations across **Leases**, **Watchers**, **Write Performance**, and **Project Governance / Client Ownership**, followed by the key questions an engineering team must answer before putting etcd into production.

### Summary of Claims

1. **Core KV Strict Serializability vs. Peripheral Subsystem & Client-Retry Fragility (**High confidence**):**
   As verified both by source analysis and by Jepsen's [`etcd 3.4.3` analysis](https://jepsen.io/analyses/etcd-3.4.3), etcd's replicated key-value state machine (`Put`, `DeleteRange`, multi-key `Txn`, linearizable `Get`, and committed `LeaseGrant`/`LeaseRevoke`) is **strictly serializable** by default (while `WithSerializable()` downgrades reads to stale committed state), and its Multi-Version Concurrency Control (`MVCC`) revision log preserves event history across leader failovers. However, the subsystems and client layers built around that core—**client retry interceptors**, **lease renewals/timers**, **watch stream control/bookmarks**, **client libraries (`client/v3`, `jetcd`)**, and **auxiliary packages (`grpcproxy`, `client/v3/ordering`, `client/v3/leasing`, `etcd/cache`)**—either bypass Raft consensus or blindly re-execute non-idempotent operations. Most notably, `jetcd` `0.5.8–0.8.4` ([jetcd#947](https://github.com/etcd-io/jetcd/issues/947) / commit `70c463c` through `0.8.4` on Maven Central; Jepsen's [`jetcd 0.8.2` analysis](https://jepsen.io/analyses/jetcd-0.8.2) tested `0.8.2` and stated `0.6.0–0.8.2`) automatically retried non-idempotent `Txn`, `Put`, and `Delete` operations on `Status.UNAVAILABLE` after the server had already committed them, causing **Lost Updates**, **Circular Information Flow (Adya G1c / retrocausal reads)**, and **Aborted Reads (Adya G1a, even when guarded by version/revision checks)**. Although `jetcd 0.8.5+` fixed the default for `KV` and `Election` ([jetcd#1444](https://github.com/etcd-io/jetcd/issues/1444) / [PR #1445](https://github.com/etcd-io/jetcd/pull/1445), commit `05f92e044`), the same duplicate-execution hazard remains in `etcd v3.7.3` and `jetcd-0.8.7` / `0.8.8` whenever callers opt into `withAutoRetry()` in `jetcd`, call `LockImpl.lock` / `LockImpl.unlock` / `LeaseImpl.grant` / `LeaseImpl.revoke` in `jetcd`, call `Lease.Grant` / `Lease.Revoke` in Go `client/v3` (`client/v3/retry.go:150-156`), use Go's `client/v3/ordering` wrapper when `Header.Revision < prevRev` (open [etcd#22086](https://github.com/etcd-io/etcd/issues/22086)), or execute single-key `Put`/`Delete` through `client/v3/leasing` (`client/v3/leasing/kv.go:242, 390`).
2. **Leases Break Both Expiration Bounds Across Failovers and Contain Severe Client Leader-Loss Bugs (**High confidence** on code paths and `#22649`/`#22081`/`#22094`; **Moderate confidence** on residual server race schedules):**
   Across leader elections, `lessor.Promote()` resets uncheckpointed lease TTLs to `ElectionTimeout + GrantedTTL`, delaying lock recovery and preventing passive TTL leases from expiring under frequent elections (`k8s#65497`). The Alpha `LeaseCheckpoint` feature (`Default: false`) ignores leases with `TTL <= 300s` and has an open bug ([#22649](https://github.com/etcd-io/etcd/issues/22649)) that silently discards Raft errors when clearing checkpoints on renewal, leaving a shorter server timer than promised to the client. Meanwhile, `WithRequireLeader` in Go `client/v3` ([#22094](https://github.com/etcd-io/etcd/issues/22094), [#22081](https://github.com/etcd-io/etcd/issues/22081)) and stream errors in Java `jetcd` (`LeaseImpl.java:273`) close or fail the user's notification channel on leader loss while **continuing to renew the "lost" lease in the background forever**.
3. **Watchers Claim "Eventual Consistency" While Admitting Events "Might Never Arrive" in a Quorum-Healthy Cluster—Forcing Clients to Poll—and `jetcd` Silently Drops Historical Events on Reconnect (**High confidence**):**
   Etcd explicitly claims to provide *"eventual consistency for Watch"* (`tests/robustness/README.md:111 @ v3.7.3`), which its own specification defines as the liveness property that components *"converge to the same view eventually"* (`tests/robustness/README.md:102 @ v3.7.3`). Yet `etcd-io/website` `content/en/docs/v3.7/learning/api_guarantees.md:36-37` states that *"events in unhealthy clusters might never arrive"*, and `content/en/docs/v3.7/learning/design-client.md:80, 106, 136` admits that even when a cluster **maintains a healthy majority quorum**, a watch stream can *"get stuck with one failed or partitioned node"* forever (`k8s#59848`). Equating eventual consistency (liveness) with prefix safety (*Ordered, Unique, Reliable*, which a permanently silent stream satisfies vacuously) is a fundamental conceptual contradiction. Worse, `WithRequireLeader` fails across nine verified paths—destroying the client's watch channel instead of failing over (`k8s#111116`), dropping partition-window events on `startRev == 0` watches, and being ignored by `grpcproxy`—while `jetcd 0.8.7` / `0.8.8` overwrites its resumption cursor with the server's tip revision upon receiving `Created` (`WatchImpl.java:267`), **silently dropping all historical events `[startRev, serverRev - 1]` if the stream disconnects during catch-up**. Because a client cannot establish a watcher with guaranteed liveness, clients are forced to bolt on periodic polling or scheduled watch restarts.
4. **Decoupling Leases from Watches Breaks Client-Side Caching and Lock Waiting (**High confidence**):**
   Because gRPC `round_robin` places a client's `LeaseKeepAlive` and `Watch` streams on different cluster members with no causal acknowledgement (`Ack-or-Expired`), a client's lease can stay alive on the leader while its watch stream stalls on a follower. In etcd's Chubby-style cache (`client/v3/leasing`), this split stalls competing writers indefinitely, optimistic client deadlines serve stale cached reads (`#19091`), and a `wc == nil` logic bug causes **every non-owner single-key `Put`/`Delete` to be applied twice** (`2` Raft proposals uncontested, `5` proposals contested).
5. **Write Performance Is Bottlenecked by Both a Synchronous Raft/WAL Pipeline and `bbolt` Copy-on-Write / Synchronous-Delete Stalls (**High confidence**):**
   Every write pays a mandatory Raft WAL `fdatasync` on a non-pipelined `raftNode` loop (`raft.go:185-336`), a 3-sync (`2x fdatasync + 1x fsync`) stall on every 64 MB WAL segment rotation (`w.cut()`), an `ext4`/`XFS` unwritten-extent journal commit penalty on every `fdatasync` into `fallocate`d blocks, and a 4-sync (`3x fdatasync + 1x fsync` when `bbolt` is dirty, or 2-sync when clean) checkpoint stall every 10,000 entries (`server.go:1215`). In the `bbolt` backend, PR [#17119](https://github.com/etcd-io/etcd/pull/17119) (`batch_tx.go:335`) forces an immediate synchronous `bbolt.Tx.Commit()` (`2x fdatasync`) on **every single `LeaseRevoke`** and **every MVCC compaction batch** because `txBuffer` cannot represent delete tombstones, while aged multi-GiB databases suffer 100ms commit lock stalls, $10\times\text{–}50\times$ CoW compaction write amplification, and stop-the-world `Defrag()` pauses.
6. **Maintainer Bandwidth Constraints, Kubernetes (`SIG-etcd`) Prioritization, and the `etcd` vs. `jetcd` Ownership Gap Create Severe Triage Latency for Non-Kubernetes Use Cases (**High confidence**):**
   Etcd is formally governed by Kubernetes `SIG-etcd` (`GOVERNANCE.md:39-41, 47 @ v3.7.3`, `OWNERS_ALIASES:1-9 @ v3.7.3`) with six active chairs/tech leads (plus `@spzala`) and twelve emeritus approvers, while `jetcd` (`OWNERS:1-6 @ jetcd-0.8.7`) has zero active maintainer overlap with core `etcd` despite being listed as a `SIG-etcd` subproject. Across multiple high-severity correctness reports, this structure has produced a documented pattern of (a) deflecting client-protocol bugs between `etcd` and `jetcd` until both issues are closed by `stale` bots or maintainers ([#14092](https://github.com/etcd-io/etcd/issues/14092), [jetcd#1072](https://github.com/etcd-io/jetcd/issues/1072)), (b) formally rejecting external consistency bug reports as inaccurate (`"at the current moment I think we can official reject Jepsen report as inaccurate"` / `"I would bet Jepsen"` in [#14890](https://github.com/etcd-io/etcd/issues/14890)) until public publication forced a same-day reversal, and (c) dismissing Watch stream liveness and disconnect detection as outside Watch's purpose ([#8980](https://github.com/etcd-io/etcd/issues/8980)) or merely a *"nice to have feature"* ([#12534](https://github.com/etcd-io/etcd/issues/12534)). Organizations adopting `etcd` outside Kubernetes's narrow API envelope—or adopting `jetcd` in Java—must plan to diagnose and patch client/edge defects in-house.

## 1. Lease, Lock, and Client-Session Issues & Mitigations

### 1.1 Why Lease Issues Happen (Architectural Root Cause)
To avoid a Raft quorum write on every heartbeat, etcd replicates `LeaseGrant` and `LeaseRevoke` through Raft into `bbolt`, but keeps lease expiration timers and `LeaseKeepAlive` renewals **only in the Raft leader's volatile memory** (`server/lease/lessor.go:396-456 @ v3.7.3`). Followers set all lease expiries to `forever` (`time.Time{}`). Unlike Google's Chubby, etcd:
1. Measures leader step-down (`CheckQuorum`) in Raft ticks on `raftNode.start()` (`server/etcdserver/raft.go:183 @ v3.7.3`), which freezes during WAL `fdatasync` disk stalls while `lessor.runLoop()` continues expiring leases on wall-clock time in another goroutine.
2. Emits expiry-driven `LeaseRevokeRequest` proposals with **no Raft term or epoch** (`api/etcdserverpb/rpc.proto:889-894 @ v3.7.3`), while `go.etcd.io/raft/v3` automatically forwards proposals from followers to the current leader (`raft.go:1718-1729 @ v3.7.0`).
3. Overloads a single Lease API for both short-lived active coordination sessions (which need failover extensions) and passive 1-hour TTL garbage collection (which breaks when failover extensions reset TTLs).

### 1.3 Deployment & Application Mitigations for Leases, Locks, and Client Retries

1. **Always fence state mutations and external actions with MVCC revisions (`CreateRevision` / `ModRevision`), and verify `Election` ownership after `Campaign()`:**
   As demonstrated by Jepsen's `etcd 3.4.3` lock analysis (§3.2), never rely on `Session.Done()`, `Mutex.Lock()`, or local lease timers alone for mutual exclusion. Guard every etcd write with a transactional compare (`If(Mutex.IsOwner())` i.e. `CreateRevision(lockKey) == myRev`, or `Election.Proclaim()`), pass `myRev` as a monotonically increasing fencing token (Chubby sequencer) to external storage or services, and explicitly verify key ownership (`Proclaim` or `Get(e.Key())`) after `Election.Campaign()` returns (`election.go:93-106`).
2. **Use `jetcd >= 0.8.8` (at minimum `>= 0.8.5`), never enable `withAutoRetry()` on non-idempotent writes or CAS transactions, and never use Go `client/v3/ordering` on mutable `Txn`s:**
   - Upgrading to `jetcd >= 0.8.5` is mandatory to pick up `Errors.isRetryableForNoSafeRedoOp` ([jetcd#1444](https://github.com/etcd-io/jetcd/issues/1444) / [PR #1445](https://github.com/etcd-io/jetcd/pull/1445), fixing the Jepsen `jetcd 0.8.2` consistency violations), and `jetcd >= 0.8.8` adds fixes for clean keepalive stream closes ([#1383](https://github.com/etcd-io/jetcd/issues/1383) / [PR #1628](https://github.com/etcd-io/jetcd/pull/1628) / `42b3f96e1`) and gRPC reconnect backoff resets ([#1616](https://github.com/etcd-io/jetcd/issues/1616) / [PR #1617](https://github.com/etcd-io/jetcd/pull/1617) / `dc4fc009c`).
   - Do **not** set `PutOption.Builder.withAutoRetry()`, `DeleteOption.Builder.withAutoRetry()`, or `TxnOption.Builder.withAutoRetry()` unless the operation is strictly idempotent and its return value (`PrevKv`, `Version`, `isSucceeded()`) is not used for control flow; as Jepsen `jetcd 0.8.2` §3.3 proved, even a CAS transaction guarded by `If(ModRevision == v)` returns a false negative (`isSucceeded() == false`) if retried after its first attempt committed.
   - In Go, do **not** wrap mutable transactions in `client/v3/ordering.NewKV` ([#22086](https://github.com/etcd-io/etcd/issues/22086)).
3. **Do NOT enable `--feature-gates=LeaseCheckpoint=true` on `v3.7.3`:**
   Leave `LeaseCheckpoint` disabled until open bug [#22649](https://github.com/etcd-io/etcd/issues/22649) (`server/etcdserver/server.go:401-402`) is patched (PR [#22650](https://github.com/etcd-io/etcd/pull/22650)).
4. **Do NOT pass `WithRequireLeader(ctx)` to `clientv3.Lease.KeepAlive(ctx, id)` on `v3.7.3`:**
   Use default contexts on `KeepAlive` (as `concurrency.NewSession` does) or patch `closeRequireLeader()` (`client/v3/lease.go:376-411`, PRs [#22087](https://github.com/etcd-io/etcd/pull/22087), [#22253](https://github.com/etcd-io/etcd/pull/22253), [#22291](https://github.com/etcd-io/etcd/pull/22291)) to prevent zombie renewals ([#22094](https://github.com/etcd-io/etcd/issues/22094)) and channel corruption ([#22081](https://github.com/etcd-io/etcd/issues/22081)).
5. **In Java `jetcd`, explicitly close the `CloseableClient` inside `StreamObserver.onError()`:**
   Any application using `leaseClient.keepAlive(leaseId, observer)` must call `closeableClient.close()` inside `observer.onError(t)` so `jetcd` removes the lease from `keepAlives` instead of renewing it forever in the background.
6. **For critical leader election / heartbeats or strict TTL expiration, prefer explicit MVCC keys with CAS over native etcd leases:**
   Follow Kubernetes's pattern (`coordination.k8s.io/v1` `Lease` in `pkg/registry/coordination/lease/storage/storage.go:36-50`): store a plain MVCC key with an explicit timestamp field updated via compare-and-swap (`ModRevision`). This avoids `Promote()` TTL resets and leader-memory split-brain at the cost of one Raft write per renewal. If native leases are used to batch-expire objects, cap attachments at $\le 500\text{–}1,000$ keys per lease.
7. **Do NOT use `client/v3/leasing` or `etcd grpc-proxy --experimental-leasing-prefix` in production:**
   The package is unmaintained and contains severe correctness and write-amplification bugs.

## 2. Watcher, Cache, and Proxy Issues & Mitigations

### 2.1 Why Watcher Issues Happen (Architectural Root Cause & The "Eventual Consistency" Contradiction)
Every watched key-value mutation goes through Raft into each member's local MVCC `bbolt` history (`server/storage/mvcc/watchable_store_txn.go:22-47 @ v3.7.3`), so committed events are never lost on disk when a leader fails over. However, **watch stream operations (`WatchCreateRequest`, `WatchProgressRequest`, `ProgressNotify`, and stream liveness) completely bypass Raft and linearizable `ReadIndex`** (`server/etcdserver/api/v3rpc/watch.go:340-400, 558-570 @ v3.7.3`).

This architectural split produces a profound conceptual contradiction in etcd's specification:
- On one hand, etcd claims to implement **eventual consistency** for Watch: *"Etcd provides strict serializability for KV operations and eventual consistency for Watch"* (`tests/robustness/README.md:111 @ v3.7.3`), defining eventual consistency on line `102` as: *"Components may temporarily see different data after an update **but converge to the same view eventually**."*
- On the other hand, etcd's API guarantee documentation states: *"However, there is no limit and events in unhealthy clusters might never arrive"* (`etcd-io/website` `content/en/docs/v3.7/learning/api_guarantees.md:36-37`), and its client design specification admits that even when **the cluster as a whole maintains a healthy majority quorum and is actively committing writes**, *"it is possible that balancer gets stuck with one failed or partitioned node"* and *"Streaming request may get stuck with a partitioned node"* (`content/en/docs/v3.7/learning/design-client.md:80, 106, 136`; see also `client/v3/watch.go:82-83 @ v3.7.3`).

In distributed systems theory, **eventual consistency** is a **liveness (convergence)** guarantee: if a cluster has quorum, all non-faulty subscribers must eventually receive committed updates. Etcd's Watch properties (*Ordered, Unique, Atomic, Reliable*) only define **prefix safety** (if events arrive, they arrive in revision order without gaps—a property that an empty, permanently silent stream satisfies vacuously). Equating *"converge to the same view eventually"* with *"might never arrive"* when a single member of a quorum-healthy cluster is partitioned or apply-stalled is a contradiction in terms. Worse, because a client cannot establish a watcher with guaranteed liveness—and cannot detect from the watch stream alone that its serving member has silently stopped delivering events—the push-subscription utility of Watch is negated unless the client bolts on **periodic polling** (linearizable `KV.Get` `ReadIndex` checks or scheduled watch restarts; notably, [Jepsen's `etcd 3.4.3` watch workload](https://jepsen.io/analyses/etcd-3.4.3) at `src/jepsen/etcd/watch.clj:139-212, 235-267 @ b47cc40` [`:131-204, 227-255 @ 0.1.0`] observed gap-free delivery specifically because it watched for only 0–5 seconds at a time and actively reconnected at `(inc revision)` [`last_seen_revision + 1`] on every iteration).

### 2.3 Deployment & Application Mitigations for Watchers

1. **Never open watches at `startRev == 0`; always use List-then-Watch with `WithRev(listRev + 1)`:**
   Perform an initial `Get` / list, record `resp.Header.Revision`, and open the watch at `WithRev(resp.Header.Revision + 1)`. Maintain `lastProcessedRev` in your application.
2. **Enable HTTP/2 keepalive pings (`DialKeepAliveTime` / `DialKeepAliveTimeout`) and `WithRequireLeader(ctx)`—and handle channel closure by re-watching from `lastProcessedRev + 1`:**
   - In Go `clientv3`, `DialKeepAliveTime` defaults to `0` (disabled); explicitly set `DialKeepAliveTime = 30s` and `DialKeepAliveTimeout = 10s` (as Kubernetes does in `staging/src/k8s.io/apiserver/pkg/storage/storagebackend/factory/etcd3.go:63-64`).
   - Wrap **both** `Watch` and `RequestProgress` contexts in `clientv3.WithRequireLeader(ctx)`. Because `clientv3` and `jetcd` close the watch on `ErrNoLeader` (and `clientv3` may drop the error after `250ms`), treat *any* watch channel closure as a retryable signal to re-open the watch at `WithRev(lastProcessedRev + 1)` (relocating to a full re-list only on `ErrCompacted`).
3. **Poll for liveness and never trust `RequestProgress` alone for linearizable cache reads (apply Kubernetes `KEP-2340` or periodic watch verification):**
   Because Watch provides only prefix safety—not eventual-convergence liveness—when a serving member is minority-partitioned or apply-stalled, and because `RequestProgress` returns a replica's unfenced local revision (and can be starved across a multiplexed gRPC stream by `#20242`), clients must bolt on polling:
   - Any cache serving linearizable reads must first issue a cheap linearizable `KV.Get(ctx, "/", WithCountOnly(), WithLimit(1))` to obtain the quorum `ReadIndex` revision $R_{\text{lin}}$, wait for the watch cache to reach $R_{\text{lin}}$, and fall back to a direct etcd read on timeout (`KEP-2340`).
   - Background watch consumers that do not serve on-demand linearizable reads must periodically poll the cluster's linearizable revision (via `KV.Get` with `ReadIndex`) or restart/rotate watches when the local watch bookmark lags behind $R_{\text{lin}}$ for longer than a staleness threshold.
4. **Do NOT rely on `jetcd 0.8.7` / `0.8.8`'s internal watch resumption for historical watches:**
   In Java, either patch `WatchImpl.WatcherImpl.onNext` (`WatchImpl.java:256-313`: on `Created` at `:267`, leave `this.revision` unchanged when `this.revision > 0` and set `response.getHeader().getRevision() + 1` only when `this.revision == 0`; on `ProgressNotify` at `:293`, advance via `Math.max(revision, response.getHeader().getRevision() + 1)`, and at `:312` guard `response.getHeader().getRevision() > 0` with the same `Math.max(..., + 1)` so `Header.Revision == 0` cannot reset `this.revision`) or manage reconnection in application code using your own `lastProcessedModRevision + 1`.
5. **Drain `WatchChan` promptly and avoid burst cancellations ($>16$) on a shared context:**
   To avoid unbounded `ws.buf` growth, the `250ms` close-error drop, and the `#18879` 4-way cancellation deadlock, drain `WatchChan` into a bounded application queue and rate-limit concurrent watch cancellations.
6. **Always pass `--bump-revision <delta> --mark-compacted` during `etcdutl snapshot restore`:**
   Ensure any restored cluster starts at a revision strictly higher than any revision previously observed by clients, forcing watchers to receive `ErrCompacted` and re-list cleanly ([#14303](https://github.com/etcd-io/etcd/issues/14303)).
7. **Do NOT deploy `grpcproxy` for watch multiplexing or use `etcd/cache` in `v3.7.3`:**
   Both contain unfixed liveness/event-loss bugs ([#21813](https://github.com/etcd-io/etcd/issues/21813), [#19710](https://github.com/etcd-io/etcd/issues/19710), [#22614](https://github.com/etcd-io/etcd/issues/22614)).

## 3. Write Performance & Persistence Pipeline Issues & Mitigations

### 3.1 Why Write Performance Issues Happen (Architectural Root Cause)
Every write in etcd `v3.7.3` traverses two distinct persistence layers:
1. **The Consensus & WAL Layer (`server/etcdserver/raft.go`, `server/storage/wal/`):** A single-threaded `raftNode` loop that synchronously writes and `fdatasync`s every batch to a 64 MB segmented Raft WAL before advancing Raft state.
2. **The State-Machine Backend (`server/storage/backend/`, `bbolt`):** An `mmap`-backed, single-writer Copy-on-Write (CoW) B+tree. While normal `Put` and `DeleteRange` operations append sequential 17/18-byte revision keys (`UnsafeSeqPut`) into an in-memory buffer (`batchTxBuffered`) committed every `100ms` or `10,000` ops, **backend deletions (`UnsafeDelete`), periodic commits, MVCC compactions, and 10,000-entry checkpoints** trigger severe lock stalls and synchronous `fdatasync` amplification.

### 3.3 Deployment Mitigations, Diagnostics, and Architectural Options

#### Step 1: Zero-Code Operational Mitigations (Apply Immediately in Production)
1. **Isolate `--wal-dir` on dedicated local NVMe storage and a separate filesystem from `--data-dir`:**
   - Never run etcd on network-attached storage with high tail `fdatasync` latency without sizing timeouts accordingly, or on shared disks.
   - Put `--wal-dir` (`member/wal`) and `--data-dir` (`member/snap/db`) on **separate filesystems/mounts** (prefer `XFS` or separate NVMe namespaces). On `ext4` (`data=ordered`), sharing a filesystem causes `fdatasync` on the Raft WAL to flush dirty OS page-cache blocks from the backend store into the `jbd2` journal ([cockroach#16624](https://github.com/cockroachdb/cockroach/issues/16624)).
2. **Keep `bbolt` database size well below RAM (`2–8 GiB`) and run `Defrag()` only as a rolling follower operation:**
   - Configure `--auto-compaction-mode=periodic` or `revision` to bound history, and monitor `etcd_mvcc_db_total_size_in_bytes` vs. `etcd_mvcc_db_total_size_in_use_in_bytes` (`server/storage/mvcc/metrics.go:171-194`).
   - Never run `etcdctl defrag` on the active leader or across all nodes simultaneously: defragment followers one at a time, then call `MoveLeader` before defragmenting the former leader.
3. **Tune batch and checkpoint flags for write-heavy workloads:**
   - Increase `--snapshot-count` (default `10,000`, e.g., to `50,000–100,000`) if the every-10,000-entry `s.snapshot()` 4-sync checkpoint spike is visible in p99 latency (trading slightly longer WAL replay on crash recovery).
   - Tune `--backend-batch-interval` (default `100ms`) and `--backend-batch-limit` (default `10,000`) to balance commit frequency against dirty-page accumulation.
4. **Minimize native `LeaseRevoke` churn on write-heavy clusters:**
   Because every `LeaseRevoke` triggers a synchronous `bbolt` `fdatasync` (`batch_tx.go:335`), avoid creating and revoking hundreds of short-lived leases per second.

#### Step 2: 1-Day Bottleneck Diagnosis on Target Hardware (Before Changing Code)
Before considering code patches or storage engine changes, run two checks on your target hardware ([`storage-agy.md` §6](storage-agy.md), [`wal-replacement-agy.md` §6](wal-replacement-agy.md)):
1. **Prometheus Histogram Attribution:**
   - Compare `etcd_disk_wal_fsync_duration_seconds` against `etcd_disk_backend_commit_duration_seconds`.
   - If `rate(etcd_disk_backend_commit_duration_seconds_count[1m]) >> 10/s`, you are hitting the **`pendingDeleteOperations > 0` synchronous commit trap** (`batch_tx.go:335`) from `LeaseRevoke` or compaction.
   - If `rate(etcd_disk_backend_commit_duration_seconds_sum[1m]) > 0.20` (backend commit lock held $>20\%$ of wall time), `bbolt` is a primary bottleneck; if `< 0.05` and WAL fsync dominates, replacing `bbolt` alone will not help.
2. **The $2 \times 2$ `tmpfs` Ceiling Matrix (`tools/benchmark` on an aged 6 GiB DB):**
   Run `tools/benchmark` across four mount combinations: (1) WAL on disk, Snap (`bbolt`) on disk; (2) WAL on disk, Snap on `tmpfs` (**exact ceiling of replacing `bbolt` alone**); (3) WAL on `tmpfs`, Snap on disk (**exact ceiling of optimizing the WAL alone**); and (4) both on `tmpfs` (**combined ceiling**).

#### Step 3: Surgical Patches vs. Full Persistence Redesign (If Maintaining a Fork)
If Step 2 proves that etcd's storage layer cannot meet your throughput or p99 latency targets with operational tuning alone:
- **Option 1 — Surgical 80-Line `txBuffer` Tombstone Patch ([`storage-agy.md` §5.2](storage-agy.md)):**
  Add a `deleted bool` tombstone marker to `txBuffer` (`server/storage/backend/tx_buffer.go`) and remove `|| t.pendingDeleteOperations > 0` from `batchTxBuffered.Unlock()` (`batch_tx.go:335`), plus remove redundant `ForceCommit()` in `kvstore_compaction.go:90`. This restores 100ms batching across `LeaseRevoke` and compaction with `< 100 LoC`.
- **Option 2 — Co-Designed `pebble` Backend + `RaftLogEngine` Fork ([`storage-agy.md` §3–§5](storage-agy.md), [`wal-replacement-agy.md` §3–§6](wal-replacement-agy.md) — **Moderate confidence** on ~4,150 LoC estimate and target-hardware speedup ratios):**
  - *Why `pebble` (`v2.1.7`), not `grocksdb`:* `mvcc.rangeKeys` issues $N$ backend point lookups per `Range` query; `grocksdb` pays $20,000\text{–}60,000$ `cgo` boundary crossings per 10k-key range scan and breaks static Go builds, whereas pure-Go `pebble` provides `pebble.IndexedBatch` (natively indexing delete tombstones) and zero `cgo` overhead.
  - *Why NOT a single unified LSM for both Raft log and MVCC:* Storing short-lived Raft entries inside the same LSM as MVCC state doubles compaction I/O and allows LSM L0 compaction stalls to block `r.storage.Save()`, causing Raft heartbeat timeouts and leader elections.
  - *Target Fork Architecture (~4,150 LoC across 4 modular phases — **Moderate confidence** on LoC estimate):* (1) Enable `AsyncStorageWrites` (`raft.go`) with explicit guards for open bugs `raft#551` and `raft#543`; (2) replace `wal.WAL` with `RaftLogEngine` built on `pebble/record.LogWriter` (`WriteWALSyncOffsets`, group commit, and pre-written recycled 64 MiB `.log` files that eliminate both `w.cut()`'s 3-sync stall and `ext4`/`XFS` unwritten-extent journal commits while fixing `isTornEntry`); (3) run `pebble` in `pebble.NoSync` mode (**0 `fdatasync`s** on the apply or 100ms commit path) with a background `db.LogData(nil, pebble.Sync)` checkpoint barrier; and (4) sort `revpairs` in ascending `Revision` order in `mvcc.rangeKeys` using a single forward-seeking `pebble.Iterator` (`TrySeekUsingNext`) so range reads match or beat `bbolt`.

## 4. Ecosystem Governance, Maintainer Bandwidth, and Issue-Triage Risks & Mitigations

When evaluating `etcd` and `jetcd` for production workloads—particularly **non-Kubernetes workloads** or **Java applications**—the technical defects cataloged in §1–§3 must be weighed alongside a structural ecosystem risk: **how upstream maintainers triage, prioritize, and take ownership of reported correctness issues**.

### 4.1 Structural Root Causes: Kubernetes (`SIG-etcd`) Governance, Maintainer Bandwidth, and the `jetcd` Ownership Gap

Repository governance files and commit histories in `etcd` (`v3.7.3` = `0a173d0410a9`) and `jetcd` (`jetcd-0.8.7` = `23b61f1499a5`) document three structural realities:

1. **`etcd` is formally governed by Kubernetes (`SIG-etcd`) and staffed by a small core team:**
   - Following a maintainer staffing shortage in 2023, Kubernetes created `SIG-etcd`, and in 2025 `etcd` formally linked its project governance to `SIG-etcd` (`GOVERNANCE.md:39-41, 47 @ v3.7.3`, commit `989dd8e9a`; `OWNERS:3-6 @ v3.7.3`, commit `ede3afac1`), routing new organization membership nominations through `kubernetes/org` (`Documentation/contributor-guide/community-membership.md:46 @ v3.7.3`).
   - Top-level approval in `OWNERS:3-6 @ v3.7.3` and `OWNERS_ALIASES:1-9 @ v3.7.3` rests with three `sig-etcd-chairs` (`@ivanvc`, `@jmhbnz`, `@siyuanfoundation`), three `sig-etcd-tech-leads` (`@ahrtr`, `@fuweid`, `@serathius`), and `@spzala`, while twelve former core maintainers (including original creator `@xiang90`, `@gyuho`, `@jpbetz`, `@jingyih`, `@wenjiaswe`, and `@philips`) are listed under `emeritus_approvers` (`OWNERS:7-19 @ v3.7.3`).
   - Active architectural review and triage across the entire `etcd` server, `go.etcd.io/raft`, `bbolt`, and Go `client/v3` codebase are therefore concentrated on those seven top-level approvers.
2. **Triage and testing prioritize Kubernetes's narrow API envelope (**High confidence**):**
   - Kubernetes's `kube-apiserver` uses Go `client/v3` with `waitForReady=false`, single-key `ModRevision` compare-and-swap (`Txn`), range reads, watches wrapped in `client-go`'s `reflector` (which periodically re-lists and runs `KEP-2340` health checks), and coarse object-TTL leases without `LeaseKeepAlive` streams.
   - Features and failure modes outside that Kubernetes envelope—such as Java `jetcd`, general multi-key transactions, `LeaseKeepAlive` under partition/leader churn, standalone Watch stream liveness without an external `reflector`, and `concurrency` locks/elections—receive limited upstream bandwidth unless a defect directly impacts `kube-apiserver` or attracts major public scrutiny (**High confidence**).
3. **`etcd-io/jetcd` has zero active maintainer overlap with core `etcd`:**
   - Although `jetcd` resides under the official `etcd-io` GitHub organization and is formally listed as a `SIG-etcd` subproject in `kubernetes/community/sig-etcd/README.md`, `OWNERS:1-6 @ jetcd-0.8.7` lists only three approvers: `@fanminshi` (an emeritus `etcd` approver with zero `jetcd` commits since 2022), `@vorburger` (2 commits since 2022), and `@lburgazzoli` (104 commits from 2022 through `jetcd-0.8.7`—105 through `jetcd-0.8.8`—primarily dependency and build maintenance alongside 222 / 234 `dependabot[bot]` commits).
   - No active `etcd` (`SIG-etcd`) chair or tech lead is an owner or regular maintainer of `jetcd` (`@jmhbnz` has 2 build/CI commits in `jetcd` since 2022 and is not in `jetcd/OWNERS`). Consequently, issues that cross the server/client boundary fall into an organizational void where `etcd` maintainers close tickets as *"a jetcd issue"* while `jetcd` lacks active consensus/protocol engineers to investigate them.

#### Case Study 3: Conceptual Confusion Around Watch Eventual Consistency vs. Prefix Safety (`etcd#8980` and `etcd#12534`)
As detailed in §2.1, `etcd` claims to provide **eventual consistency** for Watch (`tests/robustness/README.md:102, 111 @ v3.7.3`: *"converge to the same view eventually"*). For a push-based watch stream to satisfy eventual consistency (liveness), a stream whose serving member loses connectivity or leadership must either deliver events or fail/close so the client can fail over to an active member. Yet upstream issue history shows a persistent conceptual confusion in which maintainers treat Watch liveness and disconnect detection as outside Watch's scope or as an optional feature request:
- **Maintainer response in [etcd#8980](https://github.com/etcd-io/etcd/issues/8980) (*"Watch does not fail on complete loss of connectivity"*, filed `2017-12-06`):** When a user reported that a Watch stream hangs indefinitely upon complete network loss instead of failing, then-maintainer `@gyuho` (Gyuho Lee) replied on `2017-12-07` ([`#8980#issuecomment-350065151`](https://github.com/etcd-io/etcd/issues/8980#issuecomment-350065151)):
  > *"Again, watch is not really meant for detecting disconnects... If you want to detect connection loss, I would try `concurrency.Session` with TTL."*
- **Maintainer response in [etcd#12534](https://github.com/etcd-io/etcd/issues/12534) (*"Watch API. blocked forever even with WithRequireLeader option"*, `2020-12-09` to `2021-04-19`):** When a user demonstrated that a Watch stream blocked forever across server restarts/disconnections even when `WithRequireLeader` was explicitly enabled:
  - Contributor `@agargi` replied on `2020-12-27` ([`#12534#issuecomment-751475122`](https://github.com/etcd-io/etcd/issues/12534#issuecomment-751475122)): *"Whether a leader exists in a cluster is only checked at the time of creating a Watch... IIUC, what you are asking can be a future enhancement."*
  - After the `stale` bot marked `#12534` for closure, original `etcd` creator and lead maintainer `@xiang90` (Xiang Li) added label `area/feature` on **`2021-04-19`** ([`#12534#issuecomment-822107665`](https://github.com/etcd-io/etcd/issues/12534#issuecomment-822107665)) and commented:
    > *"It is a nice to have feature. Probably etcd should check if the server maintains leadership for long running requests."*
  - The `stale` bot then closed `#12534` in August 2021, leaving the exact failure class to resurface years later in [kubernetes#59848](https://github.com/kubernetes/kubernetes/issues/59848) and [etcd#17611](https://github.com/etcd-io/etcd/issues/17611).

This history explains *why* the contradiction in etcd's Watch specification (§2.1) has persisted: upstream maintainers have historically equated Watch correctness with **server-side prefix safety** (never emitting out-of-order revisions from MVCC), while viewing **client-observable liveness** (detecting dead/partitioned streams so the watcher actually converges) as an application-level problem or a *"nice to have feature"* (**High confidence**).

### 4.3 Production Mitigations for Governance, Triage, and Client-Ownership Risk

1. **Stay within the "Kubernetes-tested API envelope" wherever possible:**
   Design your usage around the primitives that `kube-apiserver` exercises continuously and that `SIG-etcd` actively defends: linearizable `Get`, range reads, single-revision CAS `Txn`, and Watch streams paired with periodic client-side `ReadIndex` polling / re-listing (`KEP-2340`). Avoid relying on peripheral server/client features (`client/v3/leasing`, `client/v3/ordering`, `grpcproxy`, `etcd/cache`, `LeaseCheckpoint`, or unguarded `concurrency.Election`).
2. **Treat `jetcd` as an effectively unstaffed dependency that your team must audit, wrap, and patch in-house:**
   Do not assume that because `etcd-io/jetcd` is in the `etcd-io` GitHub organization, it is maintained by the core `etcd` team. Any organization running `jetcd` in production must budget engineering capacity to diagnose client-protocol edge cases (such as `WatchImpl` cursor management, `LeaseImpl` error handling, and `LockImpl`/`LeaseImpl` retry rules) and contribute or maintain patches directly.
3. **Never rely on upstream default client retry or watch-liveness behavior without application-level guards:**
   Because core maintainers explicitly view duplicate execution protection (`#14890`, `#18424`) and watch disconnect detection (`#8980`, `#12534`) as application responsibilities, enforce CAS revision guards (`ModRevision` / `CreateRevision`) on all application mutations and implement explicit client-side watch progress monitoring.

## 5. Decision Guide for Prospective Adopters: Questions to Ask & What to Understand

If you are evaluating etcd for a new or existing production system, use the questions and principles below to determine your risk exposure before committing to deployment.

### 5.1 Eight Questions to Ask About Your Workload and Architecture

1. **How will your application use etcd Leases—for active coordination (locks/elections) or passive TTL garbage collection?**
   - *Why it matters:* If you use native leases for passive TTL cleanup (like Kubernetes `Event`s), leader failovers will reset their full TTLs (`lessor.Promote`), and enabling `LeaseCheckpoint` exposes you to bug [#22649](https://github.com/etcd-io/etcd/issues/22649). If you revoke leases at high rates ($>50/\text{s}$) or attach $>1,000$ keys to a single lease, every revocation forces a synchronous `bbolt` `fdatasync` (`batch_tx.go:335`) and risks apply-loop stalls (`k8s#96836`).
   - *Next step:* Ask whether passive expiration can be moved to a background sweeper over indexed timestamps, and whether coordination heartbeats should use CAS-updated MVCC keys (`ModRevision`) instead of `LeaseKeepAlive`.
2. **Do any of your services or external side effects rely on `Session.Done()` or `Mutex.Lock()` without transactional revision fencing?**
   - *Why it matters:* Client lease deadlines are optimistic (`receipt_time + TTL`), server failovers can prematurely revoke leases (`R1`–`R2`) or leak zombie renewals (`#22094`, `jetcd` `onError`), and `Mutex.Unlock()` is unfenced (`#22082`).
   - *Next step:* Audit every critical section to verify that all etcd writes include `If(CreateRevision(lockKey) == myRev)` and all external calls pass `myRev` as a verified fencing token.
3. **Which client library will your services use—Go `client/v3` or Java `jetcd`—and how are retries configured?**
   - *Why it matters:* In `jetcd 0.5.8–0.8.4` (`70c463c` through `0.8.4` on Maven Central; [Jepsen's `jetcd 0.8.2` analysis](https://jepsen.io/analyses/jetcd-0.8.2) tested `0.8.2` and stated `0.6.0–0.8.2`), `jetcd` automatically retried non-idempotent `Txn`, `Put`, and `Delete` operations on `Status.UNAVAILABLE` after the server had already committed them, causing Lost Updates, Circular Information Flow (Adya G1c), and Aborted Reads (Adya G1a, even on CAS-guarded transactions). While `jetcd >= 0.8.5` fixed the default for `KV` and `Election` (`05f92e044`, [PR #1445](https://github.com/etcd-io/jetcd/pull/1445)), `jetcd 0.8.7` / `0.8.8` remains pre-1.0, tests against outdated `etcd v3.5.14`, retains `UNAVAILABLE` auto-retry on `LockImpl.lock`/`unlock` and `LeaseImpl.grant`/`revoke`, silently drops historical watch events `[startRev, serverRev - 1]` if a stream disconnects after `Created` (`WatchImpl.java:267`), has an off-by-one bug on `ProgressNotify`, leaks infinite background lease renewals after `onError`, and in `0.8.7` permanently stops lease renewals on a clean server stream close (fixed in `0.8.8` via `#1383` / [PR #1628](https://github.com/etcd-io/jetcd/pull/1628) / `42b3f96e1`). Meanwhile, Go `client/v3` disables HTTP/2 keepalives by default (`DialKeepAliveTime == 0`), auto-retries `LeaseGrant`/`LeaseRevoke` on `Unavailable` (`retry.go:150-156`), lacks the `#11456` post-wait ownership check in `Election.Campaign` (`election.go:93-106`), re-executes committed mutable transactions in `client/v3/ordering` when `Header.Revision < prevRev` (`#22086`), and has open `WithRequireLeader` bugs (`#22081`, `#22094`, and the 9 watch teardown/failover failures).
   - *Next step:* If using Java, require `jetcd >= 0.8.8`, never enable `withAutoRetry()` on non-idempotent operations, and budget engineering work to wrap or patch `WatchImpl.java` and `LeaseImpl.java` before production use. In Go, avoid `client/v3/ordering` on mutable `Txn`s and verify `Election` ownership after `Campaign()`.
4. **Do your applications maintain in-memory caches via Watch—and what happens if a watch stream goes permanently silent while the cluster still has quorum?**
   - *Why it matters:* Despite claiming *"eventual consistency for Watch"* (`tests/robustness/README.md:111`), etcd Watch guarantees only prefix safety (event sequence continuity within retained history), **not** eventual convergence (liveness) or freshness. Even when the cluster maintains a healthy majority quorum, a watch on a single partitioned or apply-stalled member can silently stop delivering updates forever (`api_guarantees.md:37`, `design-client.md:136`, `k8s#59848`), and on-demand `RequestProgress` can be starved across a multiplexed gRPC stream by a single catching-up watcher (`#20242`).
   - *Next step:* Because etcd provides no way to set up a watcher with guaranteed liveness, budget client engineering to add periodic liveness polling (comparing the watch revision against a linearizable `KV.Get` `ReadIndex` per `KEP-2340` or rotating stalled watches) and verify your reconnect loop handles `ErrNoLeader` and `ErrCompacted`.
5. **What is your expected database size, write rate, compaction retention, and multi-key `Range` scan size?**
   - *Why it matters:* Below ~1 GiB with low lease churn on fast NVMe, `bbolt` performs well and write latency is bounded by Raft WAL `fdatasync`. Above 2–8 GiB with heavy churn and compaction, `bbolt` suffers 100ms commit lock stalls, CoW write amplification, and stop-the-world `Defrag()` pauses.
   - *Next step:* Run the 1-day $2 \times 2$ `tmpfs` benchmark matrix (§3.3 Step 2) on your target hardware at your projected aged dataset size before finalizing capacity plans.
6. **What is your storage hardware and filesystem topology?**
   - *Why it matters:* WAL `fdatasync` latency directly governs both write throughput and Raft leader stability (since a slow `fdatasync` freezes `raftNode` tick processing while lease timers keep running).
   - *Next step:* Confirm that each etcd member has dedicated local NVMe storage with `--wal-dir` and `--data-dir` on separate filesystems/mounts.
7. **What is your disaster-recovery and maintenance runbook for compaction, `Defrag()`, and `etcdutl snapshot restore`?**
   - *Why it matters:* Restoring a snapshot without `--bump-revision <delta> --mark-compacted` silently breaks active watchers (`#14303`), and running `Defrag()` on a live leader freezes the cluster.
   - *Next step:* Codify `--bump-revision <delta> --mark-compacted` into all backup/restore automation and enforce follower-only rolling `Defrag()`.
8. **Does your team have the in-house expertise to diagnose and patch `etcd` / `jetcd` bugs without relying on timely upstream resolution?**
   - *Why it matters:* Because `etcd` is governed by Kubernetes `SIG-etcd` with tight maintainer bandwidth focused on `kube-apiserver` and zero active maintainer overlap with `jetcd` (§4.1–§4.2), bugs outside Kubernetes's core path—or bugs in `jetcd`—have historically been deflected across repos ([#14092](https://github.com/etcd-io/etcd/issues/14092), [jetcd#1072](https://github.com/etcd-io/jetcd/issues/1072)), dismissed as application responsibilities or *"nice to have"* features ([#12534](https://github.com/etcd-io/etcd/issues/12534), [#14890](https://github.com/etcd-io/etcd/issues/14890)), or left open for 2–3+ years before resolution.
   - *Next step:* Ensure your engineering team is prepared to own client-side workarounds and upstream patches directly rather than treating non-Kubernetes `etcd` features or `jetcd` as turnkey vendor-supported components.

### 5.2 Six Core Realities Teams Must Understand Before Deploying etcd

1. **etcd is a linearizable log of revisions, not a Chubby-style session service:**
   In Chubby, locks, caches, and notifications are bound to one master-held session `KeepAlive` (`Ack-or-Expired`). In etcd, `KV`, `Lease`, and `Watch` are independent primitives that gRPC `round_robin` routes to different cluster members. Your application code—not etcd—is responsible for bridging them safely using `Revision` numbers.
2. **Watch does NOT provide eventual consistency (liveness) on its own—and `WithRequireLeader` is a blunt partition detector, not transparent failover:**
   Equating *"eventual consistency"* (`tests/robustness/README.md:102, 111`) with *"events in unhealthy clusters might never arrive"* (`api_guarantees.md:37`) when a single node in a quorum-healthy cluster is impaired (`design-client.md:80, 106, 136`) is a conceptual contradiction: Watch provides **prefix safety**, not **liveness**, and maintainers have explicitly stated that *"watch is not really meant for detecting disconnects"* ([#8980](https://github.com/etcd-io/etcd/issues/8980)) and treated active stream leadership checks as a *"nice to have feature"* ([#12534](https://github.com/etcd-io/etcd/issues/12534)). Enabling `WithRequireLeader` cancels streams on minority-partitioned nodes (`ErrNoLeader`), but it is blind to apply-loop stalls, destroys your client watch stream instead of failing over, and causes reconnections during routine 1-second elections to fail immediately. To achieve true eventual consistency, your watch consumer loop must re-open closed watches at `lastProcessedRev + 1` **and** pair Watch with periodic linearizable `ReadIndex` polling (`KV.Get`) or scheduled watch rotation.
3. **Disk I/O stalls are correctness events for Leases, not just performance regressions (**Moderate confidence** on `R1`/`R2` race schedules):**
   Because leadership step-down (`CheckQuorum`) is clocked by the same `raftNode` goroutine that blocks on `WAL.Save()` (`fdatasync`), a multi-second disk stall freezes the leader's step-down clock while wall-clock lease timers continue to run, exposing the cluster to the residual post-stall windows (`R1`–`R3`).
4. **Upstream test suites (`tests/robustness` and Antithesis) do not test `KeepAlive` or lease expiration:**
   As verified in `tests/robustness/traffic/traffic.go:50 @ v3.7.3`, etcd's linearizability robustness suite grants 2-hour leases (`7200s`) so they never expire, never calls `KeepAlive`, and disabled `ProgressNotify` delivery/liveness validation (`ValidateGotAtLeastOneProgressNotify` in `PR #20240`, tracked by `#20242`, though revision-monotonicity safety checks remain active in `tests/robustness/validate/watch.go:113-134`). Do not assume lease failover or watch progress liveness edge cases are covered by upstream CI.
5. **Avoid etcd's secondary proxy and caching packages (`grpcproxy`, `client/v3/leasing`, `etcd/cache`):**
   Production reliability in etcd is concentrated in the core `KV` store and carefully written direct `client/v3` consumers (following `kube-apiserver`'s defensive patterns). The auxiliary caching and proxy packages contain critical unfixed bugs in `v3.7.3`.
6. **Upstream triage prioritizes Kubernetes (`SIG-etcd`), and `jetcd` is not staffed by core `etcd` maintainers:**
   Do not expect rapid upstream investigation for bug reports outside Kubernetes's `kube-apiserver` usage pattern, and do not assume `etcd-io/jetcd` receives core `etcd` engineering support (§4).
