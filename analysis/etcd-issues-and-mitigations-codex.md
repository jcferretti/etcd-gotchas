# etcd: production risks and deployment mitigations

**Versions analyzed:** etcd server and Go client `v3.7.3` (`0a173d0410a9`); jetcd `jetcd-0.8.7` (`23b61f1499a5`). These were the latest stable releases on 2026-11-08. **Release update, 2026-11-09:** etcd remains at v3.7.3; [jetcd 0.8.8](https://github.com/etcd-io/jetcd/releases/tag/jetcd-0.8.8) (`a2909b8381f1`) has shipped. The analysis remains pinned to 0.8.7; the specific keepalive fix's release status is updated below.

**Upstream references:** linked beside the issues below; their open/merged states were rechecked on 2026-11-02. Watch liveness documentation and selected source paths were reviewed on 2026-11-03. Detailed evidence comes from the five Codex analyses in the appendix.

**Summary — High confidence:** consistent KV storage does not automatically provide timely expiry, safe external lock ownership, eventual watch progress, or fresh application caches. Application controls are essential. Untested failure schedules and proposed benefits are qualified separately below; their production frequency and performance magnitude are not established.

**Summary — Moderate confidence, adoption assessment:** historical gaps in responsibility for client/server correctness and prolonged issue resolution justify checking maintenance coverage for the exact client and features being adopted. Kubernetes governance and testing support improve the project's institutional footing, but do not establish equivalent coverage for every use case.

Scope: leases, watches, writes, and upstream maintenance. **High** means strong support from code, documented behavior, or a conditional correctness argument; **Moderate** marks plausible unexecuted failure schedules, maintenance-risk inferences, and design recommendations whose effectiveness still needs validation. Mitigations are recommendations; no capacity or incident-frequency measurements are available.

**Confidence review:** 2026-11-06. Ratings reassessed against the detailed analyses and their cited evidence; unexecuted failure schedules are distinguished from verified mechanisms. The original version, issue-state, and experiment dates remain unchanged.

**Jepsen review:** 2026-11-08. Both reports below, their linked issues, corrective commits, release tags, and relevant stable code were checked. This advances the verification date for the added findings only; no runtime tests or benchmarks were run.

**Maintenance and governance review:** 2026-11-09. Original issue comments, fix/release dates, governance documents, and official project histories were checked for the two sections below. Historical events and present governance are distinguished from inferences about future maintenance. This does not revalidate unrelated technical findings or issue states.

## Jepsen findings and client retry policy

**High confidence — historical evidence:** [Jepsen's etcd 3.4.3 report (2020-01-30)](https://jepsen.io/analyses/etcd-3.4.3) found no KV consistency anomalies, found ordered single-key watch histories, and identified unsafe lock use plus a missing post-wait ownership check. [Its jetcd report (2024-08-08)](https://jepsen.io/analyses/jetcd-0.8.2) traced lost updates, cyclic dependencies, and apparent aborted reads to hidden request retries in jetcd 0.6.0–0.8.2. Neither report certifies the versions analyzed here.

Strict serializability means transactions behave as an atomic serial execution respecting the real-time order of nonoverlapping calls. It must hold at the application's interface, including its client library. [Definition](https://jepsen.io/consistency/models/strong-serializable). A server can correctly execute each received transaction while a library violates that contract by presenting several executions as one call.

**High confidence — current policy:** Put, Delete, and Txn options default to `autoRetry=false`; their retry predicate excludes generic gRPC `UNAVAILABLE`, but retains the selected authentication-rejection cases. Reads still permit retry. `withAutoRetry()` explicitly restores the broader policy for the selected operation. Sources **@ jetcd-0.8.7**: [KVImpl.java:66, :98, :123](https://github.com/etcd-io/jetcd/blob/jetcd-0.8.7/jetcd-core/src/main/java/io/etcd/jetcd/impl/KVImpl.java#L66), [Errors.java:29–40](https://github.com/etcd-io/jetcd/blob/jetcd-0.8.7/jetcd-core/src/main/java/io/etcd/jetcd/support/Errors.java#L29), [PutOption.java:88](https://github.com/etcd-io/jetcd/blob/jetcd-0.8.7/jetcd-core/src/main/java/io/etcd/jetcd/options/PutOption.java#L88), [DeleteOption.java:98](https://github.com/etcd-io/jetcd/blob/jetcd-0.8.7/jetcd-core/src/main/java/io/etcd/jetcd/options/DeleteOption.java#L98), [TxnOption.java:31–46](https://github.com/etcd-io/jetcd/blob/jetcd-0.8.7/jetcd-core/src/main/java/io/etcd/jetcd/options/TxnOption.java#L31).

**High confidence — remaining correctness obligation:** A timeout or lost response can still leave a write's outcome unknown. Preserve that uncertainty; do not label it an abort or blindly repeat the mutation. A failed comparison on a later attempt does not establish that an earlier attempt failed. When retries are necessary, use an application operation ID with an atomic, retained result record, or another protocol that both suppresses duplicate effects and resolves the outcome. Ownership guards and fencing address obsolete owners; they do not identify whether a particular operation already executed. [API outcome contract](https://etcd.io/docs/v3.7/learning/api_guarantees/#operation-completed); [transaction distinction](leases-codex.md#56-jepsen-lock-and-retry-findings-at-the-pinned-releases). The record must survive the entire retry/reconciliation window; a separate marker write or premature deletion invalidates this reasoning.

**High confidence — version-specific mitigation:** The report's `retryMaxAttempts(0)` workaround applies to its affected releases. It is not required to obtain the corrected KV default in 0.8.7, and it does not disable watch resumption or lease keepalive recovery. [Separate retry mechanisms](watchers-codex.md#65-the-jepsen-kv-retry-fix-does-not-change-watch-resumption).

**High confidence — source distinction:** Go's mutable-RPC filter already requires specific preconnection error descriptions, rather than arbitrary `UNAVAILABLE` ([client/v3/retry.go:77–94](https://github.com/etcd-io/etcd/blob/v3.7.3/client/v3/retry.go#L77), [client/v3/retry_interceptor.go:371–372](https://github.com/etcd-io/etcd/blob/v3.7.3/client/v3/retry_interceptor.go#L371), both @ v3.7.3). [#18424's investigation](https://github.com/etcd-io/etcd/issues/18424#issuecomment-2388017692) did not reproduce the jetcd failure with Go; its eventual stale closure is neither a Go fix nor proof of universal retry safety.

## Leases and ownership

**High confidence — source-verified authority paths:** Ordinary renewal is leader-local; grants and revocations are replicated. Expiration decisions still need separate correctness checks. [Evidence](leases-codex.md#2-replicated-state-and-local-lease-timing).

| Risk, scenario, and impact | Deployment or application action |
|---|---|
| **Late expiry — High.** Failover restarts surviving lifetimes by default. Continuing elections can indefinitely delay cleanup or takeover; overload also delays deletion. | Do not use TTL as a hard deadline. Enforce an application expiration time, with explicit clock assumptions, when records must become unusable on time. Physical cleanup still requires availability. |
| **Early expiry with checkpointing — High, conditional.** A failed checkpoint clear can acknowledge more lifetime than installed ([#22649](https://github.com/etcd-io/etcd/issues/22649)). | Leave Alpha `LeaseCheckpoint` off until fixed and validated; [PR #22650](https://github.com/etcd-io/etcd/pull/22650) is unmerged. It defaults off. Checkpointing provides no hard deadline and normally excludes newly granted leases of five minutes or less. |
| **Stale ownership belief — High.** Delayed replies extend apparent client lifetime. Default-path stale-revocation and renewal/expiry races are additional **Moderate, untested** candidates for premature loss. | Check ownership in the **same transaction** as each protected etcd write. External destinations must enforce fencing that rejects obsolete owners. Timers, `Session.Done()`, and separate ownership reads are insufficient. |
| **Unwanted renewal — High mechanisms.** Go cleanup bugs misassociate subscribers or leave orphan renewal running ([#22081](https://github.com/etcd-io/etcd/issues/22081), [#22094](https://github.com/etcd-io/etcd/issues/22094)). jetcd can renew after an error callback. | On intentional release, explicitly revoke when all attached uses may end; otherwise verify cleanup or use a corrected client. Close jetcd registrations. Test server-side disappearance rather than trusting local notification. |
| **Stopped renewal after a clean stream end — High mechanism.** jetcd 0.8.7 lacks the shared keepalive stream's end handler. [#1628](https://github.com/etcd-io/jetcd/pull/1628) adds recovery and is included in [0.8.8, released 2026-11-09](https://github.com/etcd-io/jetcd/releases/tag/jetcd-0.8.8); release notes and tag ancestry verified. [Evidence for 0.8.7 and limits](leases-codex.md#55-jetcd-deadlines-and-errorretry-behavior). | Test graceful stream termination separately from transport errors. Validate the correction before relying on automatic recovery; the earlier KV retry fix does not address this path. No 0.8.8 runtime test was performed here. |
| **Stale unlock — High mechanism.** An ambiguous unlock retried after same-session reacquisition can delete the newer lock ([#22082](https://github.com/etcd-io/etcd/issues/22082)). | Use generation-conditional deletion, or prevent session/key reuse while old unlocks can execute. Bound acquisition waits and cancel on session loss. |

## Watches and caches

**Liveness gap — High in the mechanisms.** etcd's [own documentation claims eventual consistency for Watch](https://github.com/etcd-io/etcd/blob/v3.7.3/tests/robustness/README.md#L111), which requires eventual convergence; the [API documentation permits nonarrival in unhealthy clusters](https://etcd.io/docs/v3.7/learning/api_guarantees/#apis-to-consider). **Moderate confidence in the unexecuted partial-failure schedule:** even a direct `WithRequireLeader` watch can remain silently stale while a reachable majority commits updates. A storage-stalled member can retain a nonzero leader ID, leaving the flag's detector inactive. Client and proxy failures add other paths. [Exact quotations](watchers-codex.md#15-eventual-consistency-requires-eventual-progress); [counterexample and verification limits](watchers-codex.md#26-direct-leader-required-watches-can-remain-silently-stalled).

**Moderate confidence — proposed recovery policy; High in the stated limits of local signals:** Use direct member connections, reachable alternative endpoints, and `WithRequireLeader` as a **partial failure detector, not a liveness guarantee**. Add independent progress supervision: periodically obtain a linearizable revision, require application-processed watch coverage through it, and recover or rebuild on timeout. Watch callbacks and local keepalives/progress alone cannot reliably expose these stalls. Independent checks detect unverified progress; they cannot guarantee recovery from a blocked client. [Recovery protocol](watchers-codex.md#72-progress-supervision-without-blind-scheduled-restarts).

**High confidence — conditional freshness reasoning:** For a **linearizable cached read**, obtain the target revision **after that read begins**; wait for coverage or fail/read directly on timeout. Periodic checks cannot authorize later reads. [Freshness reasoning](chubby-perspectives-codex.md#84-a-progress-watermark-cannot-authorize-future-cached-reads).

**High confidence in the recovery invariants, assuming correct snapshot, event, and cursor handling:** Read a consistent snapshot at **R**, watch from **R+1**, and resume after the last **complete, application-processed** revision. Persist state and cursor consistently. Rebuild after compaction, uncertain continuity, or unusable events. Snapshots restore current state, not missed transitions. [Recovery](watchers-codex.md#7-consumer-recovery-and-freshness-policy).

| Current concern and impact | Action and remaining limit |
|---|---|
| **Optional gRPC proxy — High mechanisms; leader-loss discrepancy reproduced.** Leader-required metadata is mishandled, explicit progress requests are unsupported, and ended upstream broadcasts can accept new watchers ([#21813](https://github.com/etcd-io/etcd/issues/21813)). | Prefer direct member connections. If a proxy is required, validate failure signaling through the actual networked topology. |
| **Client recovery gaps.** Go can close without its final error (**High**). jetcd can skip history after disconnecting between creation acknowledgment and replay, or stop retries after a scheduled-resume exception ([#1227](https://github.com/etcd-io/jetcd/issues/1227)); these schedules are **Moderate, untested**. | Treat unexpected closure as failure. Start Go watches at explicit revisions. jetcd needs a validated correction or reconstruction on uncertainty; an explicit revision alone does not fix its cursor jump. Coordinate library/application retries. |
| **Stream interference.** Cancellation bursts can block dispatch ([#18879](https://github.com/etcd-io/etcd/issues/18879), **Moderate**); future/lagging watches suppress stream-wide requested progress (**High**). Reused explicit IDs can receive old events ([#22673](https://github.com/etcd-io/etcd/issues/22673), **High mechanism**). | Isolate critical streams from bulk cancellation and future watches. Match Go watch/progress metadata. Do not reuse explicit IDs within a stream. |
| **Optional caches.** `cache/` has a **High-confidence initialization-order defect**, with **Moderate confidence in the unexecuted v3.7.3 readiness-failure schedule** ([#22614](https://github.com/etcd-io/etcd/issues/22614)); `client/v3/leasing` has eviction defects and extra writes (**High mechanisms**), plus stale-read/writer-stall candidates (**Moderate**). | Avoid these unvalidated shortcuts. They are separate from Kubernetes's watch cache. Lease health alone cannot certify cache validity. |

## Write performance and operational headroom

**Moderate confidence — workload-dependent inference:** the following source-verified costs can combine during recovery; their combined impact is unmeasured. Each row rates the mechanism, not the expected benefit of its recommended mitigation:

| Pressure and impact | Mitigation |
|---|---|
| **High confidence — contention and buffering mechanisms:** slow watchers can slow writes. Catch-up scans hold a write-completion lock; Go buffers events without a hard limit. [#22264](https://github.com/etcd-io/etcd/issues/22264), [#16839](https://github.com/etcd-io/etcd/issues/16839). | Drain consumers, monitor lag/memory, and rebuild disposable state when excessively behind. Budget retention for outages **plus catch-up**; longer history also costs storage and replay work. |
| **High confidence — revocation work:** expiration bursts. Each revoke replicates a request and deletes every attached key in one transaction; JWT can add signing work. | Spread expirations where semantics permit. Reuse leases judiciously: fewer leases reduce requests, but oversized attachment groups create expensive deletions. Test mass expiry under load. |
| **High confidence — dependency paths:** storage/apply stalls delay reads too. WAL sync, quorum latency, ordered application, backend commits, and watches can each limit capacity. | Use durable low-latency SSDs and reliable networking; isolate I/O contention. Preserve fsync, reduce redundant writes, bound concurrency/retries, and batch carefully. Measure before tuning. [Hardware guidance](https://etcd.io/docs/v3.7/op-guide/hardware/). |
| **High confidence — documented maintenance/quota behavior:** maintenance/space exhaustion. Compaction removes replay history; defrag blocks its member; quota exhaustion restricts writes. | Alert on database size/free disk. Compact deliberately; defrag one member at a time, preserving quorum and checking recovery. Rehearse restore and cache invalidation. [Maintenance guidance](https://etcd.io/docs/v3.7/op-guide/maintenance/). |

Monitor **WAL/backend latency, committed-to-applied backlog, leader changes, client read/write tail latency, watch lag, memory, and disk headroom** together. Test production-like hardware through maintenance, expiry bursts, failure, and catch-up.

**High confidence in the cited release distinction; Moderate in the redesign assessment:** Backend/WAL replacements and asynchronous Raft storage require development and correctness validation. Mostly non-blocking defrag is on **upstream main** ([#22425](https://github.com/etcd-io/etcd/pull/22425), `d6af8028d9ce`), **absent from v3.7.3**. These are not deployment switches. [Storage](storage-codex.md), [WAL assessment](wal-replacement-codex.md).

## Adoption risk: maintenance coverage and issue resolution

**Moderate confidence — assessment from the cases below:** an adopter should budget for sustained investigation and potentially contributing client fixes. The relevant risk is that a correctness problem can remain unresolved across the server/client boundary even when reported with substantial evidence. Kubernetes's production use supports confidence in the paths it exercises; it does not establish the maintenance coverage of a Java application using different retry, lease, lock, or watch behavior.

Reassess this risk when there is demonstrated ownership, regression coverage, and a validated released fix for the required paths.

## Questions to resolve before deployment

- Do you need current state, every transition, bounded expiry, or exclusive external effects? Who enforces each guarantee?
- What staleness, takeover delay, outage, and data-loss limits are acceptable?
- Who detects silent watch stalls and triggers recovery? Does the client recover through partitions, ambiguous replies, compaction, and restore?
